## 템플릿에서 시작

HTML과 CSS를 매번 새로 만들지 않는다. 이 스킬 폴더의 템플릿을 복사해서 채운다.

1. `assets/template.html` 을 문서 경로로 복사한다.
2. `{{...}}` 자리표시자를 채우고, 예시 섹션을 실제 섹션으로 바꾼다. 쓰지 않는 예시는 지운다.
3. 카드, 표, 태그, 단계, 다이어그램, 캡처, 터미널 블록 등은 `references/components.md` 의 마크업을 그대로 쓴다. 필요한 컴포넌트가 없을 때만 `<style>` 끝에 규칙을 덧붙인다. 기존 색 토큰(`--blue`, `--red-t` 등)을 쓴다.

템플릿에 이미 들어 있는 것: 자동 반응형 크기 체계, TDS 스타일과 Pretendard, 왼쪽 고정 사이드바 목차(넓은 화면)와 상단 목차(좁은 화면), 스크롤 위치 강조, 코드 하이라이팅, react-grab, 문서 보기 토글.

## 자동 반응형

- 템플릿의 `html` 글자 크기는 브라우저 뷰포트 너비에 따라 `clamp()`로 변한다. 제목·본문·표·코드·목차와 여백은 `rem`으로 함께 조절된다. 모니터 해상도나 `devicePixelRatio`로 배율을 계산하지 않는다.
- 새 스타일도 글자·여백·너비에는 `rem`/`em`과 유동 레이아웃을 쓴다. 얇은 테두리 외에는 고정 `px` 크기, `zoom`, `transform:scale()`로 문서 크기를 덮어쓰지 않는다. 브라우저 확대와 기본 글자 크기 설정을 유지한다.
- 일반 본문은 `--reading-width` 안에서 읽고, 표·코드·그림은 카드 너비를 활용한다. 긴 본문을 추가하는 새 컴포넌트에도 이 줄 길이 제한을 적용한다. 넓은 화면을 채우려고 문장을 무제한으로 늘리지 않는다.
- 그리드는 사용할 수 있는 공간에 따라 열 수를 줄인다. 표는 `.tbl`, 다이어그램은 `.dwrap`, 코드는 `pre` 내부에서 가로 스크롤한다. 페이지 전체에 가로 스크롤이 생기거나 내용을 숨기는 방식으로 처리하지 않는다.
- 전달 전 좁은 화면(약 360px), 창 분할(약 960px), FHD/QHD 너비(1920/2560 CSS px)에서 기본/문서 보기 양쪽을 확인한다. 브라우저 확대 시 목차·카드가 재배치되고 표·코드가 페이지 밖으로 밀려나지 않는지도 확인한다. 물리 해상도와 CSS 뷰포트 너비는 같지 않을 수 있다.

## 파일

- HTML 파일 하나로 만든다. 마크다운(.md)으로 쓰지 않는다.
- 이미지는 문서 옆 `assets/` 폴더에 두고 상대경로로 참조한다.

## 목차

- 섹션을 추가하면 사이드바(`.sidebar`)와 상단 목차(`nav.toc`) 양쪽에 링크를 넣는다.
- 하위 절은 `<h3 id="...">` 를 달고 사이드바 `ol.subs` 에 `data-target` 으로 연결한다.

## react-grab

템플릿 `<head>` 에 들어 있다. 문서를 브라우저에서 보면서 요소를 골라 수정 요청할 때 쓴다.

- 문서를 넘길 때 사용법을 한 줄 덧붙인다: 요소에 마우스를 올리고 ⌘C(그 외 OS는 Ctrl+C)를 누르면 요소 정보가 복사되니 그대로 붙여 넣어 수정을 요청하면 된다.
- CDN 스크립트라 오프라인에서는 이 기능만 빠진다. 나머지 렌더링은 오프라인에서도 되어야 한다.

## 문서 보기

템플릿 오른쪽 아래 [문서로 보기] 버튼(`#viewToggle`)과 `body.doc-mode` 스타일이 들어 있다. 켜면 사이드바가 사라지고 `.wrap` 이 더 넓어지며, 카드 대신 구분선으로 이어지는 한 장짜리 문서처럼 보인다.

- 버튼 또는 `D` 키로 전환, `Esc` 로 해제. 상태는 파일 경로별로 localStorage 에 저장된다.
- 버튼, 스타일, 스크립트를 지우지 않는다. 새 컴포넌트를 추가해서 카드 배경이나 너비에 기대는 스타일을 만들면 `body.doc-mode` 에서도 깨지지 않는지 함께 맞춘다.
- 문서를 넘길 때 react-grab 안내와 함께 한 줄 덧붙인다: 오른쪽 아래 [문서로 보기] 버튼이나 `D` 키로 본문만 넓게 볼 수 있다. 일반 문장의 줄 길이는 유지된다.

## 다이어그램

- 구조도/계층도/관계도/흐름도 같은 시각화는 전부 `diagram-design` 스킬로 인라인 SVG를 만든다.
- `<pre>` 에 ├ └ ─ → 같은 문자로 트리, 박스, 화살표를 그리지 않는다. `<pre>` 는 JSON, SQL, 의사코드처럼 실제 코드나 데이터 원문에만 쓴다.

## 코드 블록

- JSON, SQL, 코드, 의사코드, HTTP 요청/응답은 `<pre>` 에 넣으면 템플릿 스크립트가 하이라이팅한다. 외부 라이브러리를 추가하지 않는다.

## 에러 로그와 콘솔 출력

에러 응답, 스택 트레이스, 콘솔 출력은 한 줄로 붙이지 않고 어두운 터미널 스타일 블록(`.term`, components.md 참고)으로 보여준다.

- 헤더 바에 요청 메서드/경로(또는 명령)와 상태 배지(예: `400 Bad Request`, 실패는 빨강).
- JSON 은 들여쓰기로 펼치고 키/문자열/숫자/구두점 색을 구분한다.
- 긴 메시지는 의미 단위로 줄을 나누고, 핵심(문제 컬럼/값, 원인 옵션, 에러 코드)에 배경색 하이라이트를 준다. 2~3색까지 쓰고 블록 아래에 색 범례를 붙인다.
- 줄 나눔이나 생략처럼 원문을 가공했으면 캡션에 적는다. 값을 지어내거나 바꾸지 않는다.

## 화면 흐름

- 앱/웹 화면, 웹뷰, 외부 서비스 연동 화면은 글로만 설명하지 않고 원문 문서나 실제 화면 캡처를 잘라 넣는다.
- 캡션에 출처(문서명, 쪽수)를 적는다.

## 시스템 연동

구간마다 누가 누구에게 보내는지, 메서드/주소/인증, 요청 본문, 응답 본문을 예시로 보여준다.

- 예시 값은 가능하면 실제 데이터(문서, 코드, 수집 데이터)에서 가져온다.
- 비밀값(키, 토큰)은 가린다. 실제 응답을 봐야 아는 값은 `<...>`, 제안 단계의 필드는 `(안)` 으로 표시한다.

## 구현 설계

- 앞으로 구현될 것이 분명한 기능은 "무엇을 해야 하는지"에서 멈추지 않고 "어떻게 구현할지"(API 안, 데이터 모델, 처리 흐름, 예외 상황)까지 쓴다.
- 제안 전에 원문 문서의 권장안/제한 사항과 현재 코드베이스(필요하면 같은 PC의 다른 프로젝트)의 비슷한 기능/패턴을 먼저 확인하고, 그 결과를 근거로 적는다.
